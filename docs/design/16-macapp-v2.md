# 16 — mac-app v2: layered compatibility, launcher bundle, store-referenced runtime

**Status:** contract (2026-10-23). Nothing implemented yet; the work is tracked under
epic #50 (sub-epics #86–#93).
**Research:** docs/19 (strategy, §5 test matrix, §6 recommendation, §7 macOS 28 risk);
#94 (where DXMT's `winemetal.so` can live, tested 2026-10-23).
**Decisions:** issue #61, settled by the owner on 2026-10-23 (1, 2, 4–7) and by #94 (3).
**Amends:** design 10 §2, §3, §10 · design 11 §1 · design 12 D3, §4, §5 · design 15 §3 ·
docs/18 §1. Each of those carries an "Amended 2026-10-23 (design 16)" note.
**Scope:** the bundle model, the on-disk layout, and the config contract between gogo and
the launcher. The individual layers (L1 scanner, L3 DB, failure dialogs, …) get their
detail in their own issues. This doc fixes only what they have to agree on.

## 0. Summary

A v2 `.app` is a **small, signed, never-written launcher**. Everything that changes after
signing lives outside it:

```
Foo.app/Contents/                       signed once, never written afterwards
  MacOS/<name>                          bash launcher (#66)
  Resources/gogo-launch.toml            what to run: gogid, runtime, renderer, exe, args, env
  Resources/launch.conf                 shell mirror of the TOML (generated by gogo)
  Resources/<icon>, LICENSE-*.txt
  Info.plist

~/Library/Application Support/gogo/     the "state dir" (06 §1)
  runtimes/<id>/<ver>/{engine,Frameworks}             L0, shared by every game
  runtimes/<id>/<ver>+<renderer>-<rver>/engine        derived runtime (decision 3)
  renderers/<id>/<ver>/<arch>/                        renderer payloads as downloaded
  games/<gogid>/prefix/                               Wine prefix (built by gogo)
  games/<gogid>/game/                                 game files (APFS clone of the depot tree)
  games/<gogid>/state.toml                            what gogo last applied + stamp
  games/<gogid>/launch.conf                           effective launch config (L0–L4 merged)
  compat/<gogid>.toml                                 L4 user override
```

The five compatibility layers from docs/19 §6 are evaluated by gogo, never by the
launcher:

```
flags  >  L4 user override  >  L3 compat DB  >  L2 GOG-native  >  L1 auto renderer  >  L0 default runtime
```

The launcher only sources files gogo wrote, compares a stamp, and either execs Wine or
asks gogo to bring the prefix up to date first.

`--portable` (#84) keeps today's fat bundle (engine + prefix + game inside the `.app`) for
copying to another Mac. Everything below is about the default, non-portable bundle.

## 1. Decision 1: `gogo-launch.toml` is the source of truth, `launch.conf` is its mirror

**Settled:** the TOML is the source of truth. gogo also writes a shell-sourceable
`launch.conf` generated from it. The bash launcher only ever **sources `launch.conf`**,
and only gogo writes either file.

**Why:** bash can't parse TOML without a dependency the launcher shouldn't have (a
second binary inside the bundle, or `python3`, which macOS no longer ships). TOML stays
the format gogo reads, diffs and validates. The mirror is a mechanical projection, so
the two can't drift as long as gogo is the only writer.

### 1.1 Schema (`schema = 1`)

```toml
schema   = 1
gogid    = "1146738698"
title    = "Carmageddon TDR 2000"
runtime  = "winecx/24.0.7_7"          # <id>/<ver> in the store (decision 6)
renderer = "wined3d"                  # wined3d | dxmt/v0.80 | cnc-ddraw/7.1.0.0 | d3dmetal/<ver>
exe      = 'C:\GOG\Carmageddon TDR 2000\TDR2000.exe'
workdir  = 'C:\GOG\Carmageddon TDR 2000'
args     = ["-f"]
env      = { WINEMSYNC = "1" }
dll_overrides = { ddraw = "n,b" }     # what the launcher exports in WINEDLLOVERRIDES
verbs    = []                         # winetricks verbs; applied by setup, never by the launcher

[gogo]
path  = "/Users/me/.nix-profile/bin/gogo"   # recorded at build (decision 2)
state = "/Users/me/Library/Application Support/gogo"
```

- Unknown keys are an error for gogo (`deny_unknown_fields`); `schema` gates any future
  change. A bundle with a newer `schema` than the running gogo is refused with "upgrade
  gogo", never half-read.
- `gogo.path` is the path gogo was **invoked as**, not `canonicalize`d: a Nix or Homebrew
  profile symlink survives upgrades, while the resolved `/nix/store/…` path does not.

### 1.2 Two copies of `launch.conf`

| File | Written by | When | Contents |
|---|---|---|---|
| `Foo.app/Contents/Resources/launch.conf` | gogo build | once, before signing | mirror of the bundle's TOML (L0–L3 + build flags as baked) |
| `games/<gogid>/launch.conf` | `gogo mac-app setup` | build, and whenever the stamp is stale | the **effective** config: bundle TOML with L4 applied, plus `RUNTIME_DIR`, `PREFIX`, `STAMP` resolved to absolute paths |

The launcher sources the bundle copy first, then the state copy if it exists. Values are
POSIX single-quoted by the same `sh_quote` the current `bundle.rs` uses. No
command substitution and no code, only assignments.

*Implemented in #66 (`macapp/launch.rs`), with these details:*

- Lists are bash arrays (`ARGS=('-f')`, `ENV=('K=V')`, `VERBS=()`);
  `DLL_OVERRIDES` is Wine's own `k=v;k2=v2` string.
- The state copy also carries `WINE`, `WINESERVER` and `FRAMEWORKS`, next to
  `RUNTIME_DIR`, `PREFIX` and `STAMP`.
- Paths under the state dir are written **relative to it**
  (`PREFIX='games/<gogid>/prefix'`), not absolute, and the launcher resolves them
  against the state dir it finds: `gogo.state` if that directory exists, else
  `~/Library/Application Support/gogo`. A state dir copied to another account (the VM
  harness, a new Mac) then works unchanged. Runtimes outside the store stay absolute.
- A runtime outside the store (brew, a GPTK mount, `--runtime path`) is referenced as
  `runtime = "path:<root>"`. It works, but it can't be swapped or GC-tracked.
- Build flags are baked into the bundle TOML (this table's first row). Only
  `--retarget` writes L4 (§7), so a build never creates an override file the user
  didn't ask for.

## 2. Decision 2: gogo builds the prefix; the launcher re-runs setup only when stale

**Settled:** gogo creates and populates the prefix **at build time**, into
`games/<gogid>/prefix`. The launcher calls `gogo mac-app setup <gogid>` (the absolute
path recorded in `gogo.path`, then `gogo` on `PATH` as a fallback) **only** when the
config stamp is stale or the prefix is missing. If it can't find gogo, it launches as-is
and logs that.

**This departs from docs/19 §6.5**, which says the prefix is "created on first launch by
the user's own wine", with first launch running "create prefix → apply L2/L3/L4 → launch".
What changes, and why:

- **Same user, same Mac, so "the user's own wine" is still what runs.** Non-portable
  bundles are built by the person who plays them, into their own state dir, with the
  runtime from their own store. The prefix gets the right username without waiting for
  first launch. The builder-home leak (#55) came from Wine's default home-folder symlinks
  and `z:` → `/`, and decision 4 removes those. Who runs `wineboot` was never the cause.
- **The tools are present at build time and not in the launcher.** Prefix setup needs
  winetricks, gogo's `cabextract`/`7z` shims (design 12 D5), verb downloads (network),
  and registry writes. Putting that in a bash launcher would mean shipping or locating
  all of it at double-click time. gogo already has it.
- **Failures surface where they can be read.** A failed verb or `wineboot` at build
  prints in the terminal next to the command that caused it. At first launch the same
  failure would turn into a dialog after a long silent pause, and a broken prefix.
- **First launch is fast and boring.** The double-click does what the user expects.
- **docs/19's "first launch" behaviour is kept where it matters.** The stamp check means
  an edited L4 override, a `--retarget`, or a deleted prefix is applied on the next
  launch, without a rebuild, exactly as docs/19 wanted. Only the *first* setup moved
  earlier.

What it costs: a non-portable bundle copied to another account or Mac has no prefix
there. It needs gogo installed on that side to be set up (or the bundle should have been
built `--portable`).

### 2.1 The stamp

- `STAMP` = sha256 over the **inputs** of the effective config, in a fixed order: the
  bundle's `gogo-launch.toml` bytes, then the L4 file's bytes (or an empty marker when
  there is none; #66 uses zero bytes, so a missing and an empty L4 file stamp alike). The launcher can compute exactly this with `/usr/bin/shasum -a 256`
  and nothing else.
- `setup` records the stamp it applied in `games/<gogid>/launch.conf` (`STAMP=`) and in
  `state.toml`.
- Launcher: prefix missing, or computed stamp ≠ recorded stamp → run setup, then
  re-source the state `launch.conf`. Setup is idempotent: it re-applies registry, verbs,
  overrides and renderer files, and never deletes the prefix or the saves in it.
- L3 updates (a newer compat DB) reach a game when gogo next runs `setup` for it, not on
  every launch. The launcher doesn't know the DB exists.

### 2.2 `gogo mac-app setup <gogid>`

Reads the bundle TOML (path recorded in `state.toml`), L3 and L4, then installs or derives
the runtime it needs (decision 3, network allowed under design 12 D8), creates or updates
the prefix, writes the state `launch.conf`, and exits 0. Exit codes as for `mac-app`
(07 §2). The same function runs at the end of every build, so build and launch never
take different paths into the prefix.

## 3. Decision 3: renderers that replace Wine builtins live in a derived runtime

**Settled by #94** (overturns the pre-filled default "PE DLLs per prefix, `winemetal.so`
added to the store runtime").

Tested on `WineCX24.0.7_7` with `dxmt-v0.80-builtin.tar.gz`, using a windowless
`D3D11CreateDevice` probe, `WINEDEBUG=+loaddll` and `DYLD_PRINT_LIBRARIES` (the full
matrix is in the #94 comment):

| Placement | Result (64- and 32-bit) |
|---|---|
| `WINEDLLPATH=renderers/dxmt/v0.80` | wined3d loads; the engine's own `lib/wine` is searched first |
| PE DLLs in `system32`/`syswow64` + `n,b` | wined3d loads; the DLLs carry the builtin marker, so Wine swaps in the engine's copies |
| `winemetal.so` added to the store runtime + PE per prefix | wined3d loads; the `.so` is inert |
| **APFS clone of the engine + DXMT over `lib/wine/`** | **DXMT loads**: FL 11.0, `winemetal.so` `dlopen`ed from the derived tree |

Wine's loader (`dlls/ntdll/unix/loader.c`, the same in 9.0 and 11.0) always puts the
engine's own dll dir ahead of `WINEDLLPATH`, and it finds a unix lib only next to the
builtin PE it loaded. A shared, unmodified runtime therefore cannot be made to load
DXMT from outside its tree.

**Rule:**

- A renderer is either an **engine overlay** (it replaces Wine builtins: DXMT, and
  D3DMetal later) or **game-local** (cnc-ddraw: a DLL in the game dir +
  `dll_overrides`). wined3d is the engine itself and needs nothing.
- An engine-overlay renderer is installed as a **derived runtime**
  `runtimes/<id>/<ver>+<renderer>-<rver>/engine`. gogo builds it by `clonefile`ing the
  base engine and copying the renderer's `<arch>-windows`/`<arch>-unix` dirs over
  `lib/wine/`. `Frameworks/` is shared with the base: a relative symlink, since the
  engine reaches it through `DYLD_FALLBACK_LIBRARY_PATH`, not its `@rpath` (#62,
  decision 6). Measured cost: 0.75 s and ~1 MB of metadata for
  the 503 MB CX24 engine, plus the renderer's files once (~51 MB for DXMT), shared by every
  game that uses the same pair.
- The base runtime is **never modified**. A derived runtime is immutable once built:
  when either input is bumped, gogo builds a new one; it never patches one in place.
- The launcher doesn't know about derivation. The state `launch.conf` carries the
  resolved `RUNTIME_DIR`.
- No prefix copies and no `n,b` overrides for engine-overlay renderers.
- **arm64ec:** the overlay copies whatever `<arch>-*` dirs the renderer release ships
  (`aarch64-windows`/`aarch64-unix` for an ARM64EC DXMT), and the loader rule doesn't
  depend on arch. See §Open for entitlement-signed runtimes.

## 4. Decision 4: home folders are real dirs, `z:` is gone

**Settled:** `drive_c/users/<user>/{Desktop,Documents,Downloads,Music,Pictures,Videos}`
are plain directories inside `games/<gogid>/prefix`. They are never symlinks into the
real `~`. `dosdevices/z:` is removed.

**Why:** saves and logs stay with the game (Rebel Galaxy wrote into the host's
`~/Documents/My Games/` during docs/19 §5), nothing escapes into the user's real folders,
and nothing in the prefix points outside the state dir. That last point is what made
#55's signature and username leaks possible. Dropping `z:` also means a game can't
wander the whole filesystem by accident.

**Consequence:** the game dir must be reachable without `z:`.
`prefix/drive_c/GOG/<tree-name>` is a relative symlink to `../../../game`, so the
Windows path stays `C:\GOG\<tree-name>` as in design 15, and registry keys and
`goggame-*.info` paths don't change.

## 5. Decision 5: precedence

**Settled:** `flags > L4 > L3 > L2 > L1 auto > L0 default`, field by field.
Maps (`env`, `dll_overrides`) merge per key; every other field, lists included, is
replaced whole, so an L4 `verbs = []` clears L3's verbs (#65, `macapp/compat.rs`).

**Why:** the closer a source is to the user's explicit intent, the more it wins. Curated
data (L3) beats heuristics (L1) because it records an observed result. GOG's own data (L2)
beats the import heuristic because it comes from the vendor.

- Flags only exist on a gogo invocation (`mac-app`, `setup`, `--retarget`). A flag that
  has to **persist** (`--renderer`, `--runtime`) is written into L4 (§7); a flag that
  doesn't is used for that run only. This keeps "flags > L4" true without a sixth
  persistent layer, and it's what decision 7 already does for `--retarget`.
- gogo edits only the keys it owns in the L4 file (`toml_edit`, so the user's comments
  survive) and reports what it changed.
- `gogo mac-app doctor` (#79) shows the winning layer for each field.

## 6. Decision 6: store layout and GC

**Settled:**

```
runtimes/<id>/<ver>/{engine,Frameworks}           base runtimes, as pinned (sha256) and probed
runtimes/<id>/<ver>+<renderer>-<rver>/engine      derived runtimes (§3)
renderers/<id>/<ver>/<arch>/                      renderer payloads, <arch> = runtime arch (x86_64, arm64ec)
games/<gogid>/{prefix,game,state.toml,launch.conf}
```

- `state.toml` records the bundle path, the runtime and renderer refs in use, the applied
  stamp, and gogo's version. It's the store's **reference list**.
- **GC:** `gogo runtimes prune` never removes a runtime (base or derived) or a renderer
  that any `games/*/state.toml` references, and it always keeps the previous version
  (N-1) of each runtime id for rollback. There is **no automatic prune**.
- `games/<gogid>/` is removed only by an explicit command (it holds saves). A rebuild of
  the same game re-clones `game/` and keeps `prefix/`.
  *#66:* the installer lane learns the gogid only after installing, so it builds in
  `games/.build-<slug>-<pid>/` and then moves the result into place. If an older
  `prefix/` exists for that game, it's renamed to `prefix.old-<timestamp>`, never
  deleted. The depot lane keys the dir by `rootGameId` from `goggame-*.info`.
  `gogo runtimes prune` already refuses ids that a `state.toml` references. The N-1
  rule is left for the GC work.
- Today's flat entries (`runtimes/wine-staging/11.18/…`, design 12 §4) stay readable:
  an entry without `engine/` is treated as an engine with no `Frameworks/`.
- *#62 (the CX engine, `winecx/24.0.7_7`):* the entry is
  `runtimes/winecx/24.0.7_7/{engine,Frameworks,NOTICES.txt}`. `engine/` is the
  contents of Sikarugir's `wswine.bundle`. `Frameworks/` holds the top-level `*.dylib`s
  (symlinks kept) of Sikarugir Template 1.0.24's `Contents/Frameworks`;
  `GStreamer.framework` is left out. `NOTICES.txt` holds the engine's licence and one
  licence line per dylib, and builds copy it into the bundle as `LICENSE-runtime.txt`.
  Both archives are pinned by sha256 in the catalog, and GitHub's asset digest must
  agree. Sikarugir publishes every engine under a single `v1.0` release, so the pin
  names the asset, not the tag. The install is probed with `wine --version` and
  `wineserver --version` (wineserver links `libinotify`).
- *#62, how the engine finds `Frameworks/`:* through `DYLD_FALLBACK_LIBRARY_PATH`,
  set by gogo on every Wine call (probe, `wineboot`, `reg`, installers, winetricks) and
  by the launcher from `FRAMEWORKS`. Mimicking the wrapper's
  `Contents/Frameworks/wswine.bundle` layout isn't enough: the rpath
  (`bin/../../`) would find the dylibs, but win32u `dlopen`s FreeType by leaf name,
  which only the fallback path finds. Without it, "Wine cannot find the FreeType
  font library" appears even in that layout (tested 2026-10-23). With the fallback
  path set, the layout doesn't matter, so decision 6's `{engine,Frameworks}` is
  kept as written. For §3's derived runtimes this means `Frameworks` is a relative
  symlink to the base entry's `Frameworks/`, and nothing is copied.

**Why:** one copy of each engine per Mac (bundles today carry 0.5–0.85 GiB of runtime
each, docs/19 §5), runtimes swappable in place (the macOS 28 path, docs/19 §7.3), and
game files and saves that survive a bundle rebuild.

## 7. Decision 7: `--retarget` writes L4, never the bundle

**Settled:** `gogo mac-app --retarget <bundle|gogid> --runtime <id>` (and `--renderer`)
writes the choice into `compat/<gogid>.toml` (L4). The signed bundle is never touched.
The next launch sees the stamp change and runs setup.

**Why:** the bundle seal stays valid (#53), retargeting is as cheap as editing a file,
and the user's override and gogo's retarget are the same mechanism, so `doctor` explains
both the same way.

## 8. Launcher contract (#66)

In order, in bash, with no other dependencies than `/usr/bin/shasum` and `osascript`:

1. `source Resources/launch.conf`, then `games/<gogid>/launch.conf` if present.
2. Compute the stamp (§2.1). If it's stale or the prefix is missing, run `gogo mac-app
   setup <gogid>` (`GOGO_PATH`, then `PATH`) and re-source. If there's no gogo, log the
   fact and continue.
3. Export `WINEPREFIX`, `WINEDLLOVERRIDES`, `env`; `cd` to the workdir; run Wine from
   `RUNTIME_DIR` with its log teed to `~/Library/Logs/gogo/<gogid>/` (#77).
4. Early-exit dialog and "try next renderer" are #78. They write L4 through gogo, never
   directly.

*As implemented in #66:*

- Setup is called as `gogo mac-app setup <gogid> --bundle <this .app>`, so a bundle
  the user moved to `/Applications` updates `state.toml`.
- The launcher stays Wine's parent (it doesn't `exec`), so it can tear down.
- After Wine exits, the launcher waits on `wineserver -w`, because a launcher exe may
  have started the real game and exited.
- On `INT`/`TERM`/`HUP` it tears down (#42). It sends `TERM` to the game's process
  group, then runs the store runtime's `wineserver -k` with this prefix. If this
  prefix's wineserver is still alive after 5 s, it gets `SIGKILL`. That server is
  found by its cwd, `/tmp/.wine-<uid>/server-<dev>-<ino>` of the prefix: Wine's
  services `setsid()` into their own groups, so the process group can't be used to
  find them. What's left of the game's group also gets `SIGKILL`, and the launcher
  logs it.
- A `SIGKILL` of the launcher itself can't be trapped.
- Logs go to `~/Library/Logs/gogo/<gogid>/{launch,wine}.log`; #77 refines them.

The launcher never writes inside the bundle, never runs winetricks, and never modifies
the store.

## 9. Testing (08 conventions)

- Unit: TOML ⇄ `launch.conf` projection (golden), stamp computation matching a
  reference `shasum` output, precedence merge per field, `prune` reference rules,
  derived-runtime overlay against a fake engine tree.
- Integration (`macapp_pipeline.rs`): build with a fake runtime → assert nothing under
  `Foo.app` changes after signing; edit the L4 file → the launcher (run against a fake
  `gogo`) calls setup exactly once.
- VM (#68): `scripts/vm-test.sh` gains a store and state-dir seeding step, since a v2
  bundle alone isn't enough to launch.

## Open

1. ~~**Missing prefix and no gogo.**~~ *Settled in #66 as proposed:* with no prefix and
   no gogo, the launcher shows a dialog and stops. It launches as-is only when the prefix
   exists but is stale.
2. **Entitlement-signed runtimes** (docs/19 §7.2): a vendor-signed ARM64 runtime may not
   allow being cloned with files added (sealed resources). If so, an engine-overlay
   renderer has to come from the vendor's own build. Re-check when such a runtime exists
   (#82).
3. **D3DMetal as a derived runtime** (#71): expected to use the same mechanism. Not
   tested yet.
4. **The `C:\GOG\<name>` symlink** to `games/<gogid>/game`: Wine follows it, but games that
   canonicalize their own path (and installers run into it) should be checked in the VM
   during #67.
5. **Migrating today's fat bundles:** not planned. They keep working as they are, and a
   rebuild produces a v2 bundle. Decide whether `doctor` should say so.
6. **Removing a game** (`games/<gogid>/` holds saves): command name and confirmation
   flow aren't designed yet.
7. **L3 freshness:** when gogo fetches a newer compat DB, should it re-run `setup` for
   affected games or leave that to the next explicit command? (#74)
