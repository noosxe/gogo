# 16 — mac-app v2: layered compatibility, launcher bundle, store-referenced runtime

**Status:** contract (2026-10-23). Partly implemented (#62, #63, #65–#68, #70; the
notes in *italics* say how); the rest is tracked under epic #50 (sub-epics #86–#93).
**Research:** docs/19 (strategy, §5 test matrix, §6 recommendation, §7 macOS 28 risk);
#94 (where DXMT's `winemetal.so` can live, tested 2026-10-23).
**Decisions:** issue #61, settled by the owner on 2026-10-23 (1, 2, 4–7) and by #94 (3).
**Amends:** design 10 §2, §3, §10 · design 11 §1 · design 12 D3, §4, §5 · design 15 §3 ·
docs/18 §1. Each of those carries an "Amended 2026-10-23 (design 16)" note.
**Scope:** the bundle model, the on-disk layout, and the config contract between gogo and
the launcher. The individual layers (L1 scanner, L3 DB, failure dialogs, …) get their
detail in their own issues. This doc fixes only what they have to agree on.

## 0. Summary

A v2 `.app` is a **small, signed, never-written launcher**. Everything that changes after
signing lives outside it:

```
Foo.app/Contents/                       signed once, never written afterwards
  MacOS/<name>                          bash launcher (#66)
  Resources/gogo-launch.toml            what to run: gogid, runtime, renderer, exe, args, env
  Resources/launch.conf                 shell mirror of the TOML (generated by gogo)
  Resources/<icon>, LICENSE-*.txt
  Info.plist

~/Library/Application Support/gogo/     the "state dir" (06 §1)
  runtimes/<id>/<ver>/{engine,Frameworks}             L0, shared by every game
  runtimes/<id>/<ver>+<renderer>-<rver>/engine        derived runtime (decision 3)
  renderers/<id>/<ver>/<arch>/                        renderer payloads as downloaded
  games/<gogid>/prefix/                               Wine prefix (built by gogo)
  games/<gogid>/game/                                 game files (APFS clone of the depot tree)
  games/<gogid>/state.toml                            what gogo last applied + stamp
  games/<gogid>/launch.conf                           effective launch config (L0–L4 merged)
  compat/<gogid>.toml                                 L4 user override
```

The five compatibility layers from docs/19 §6 are evaluated by gogo, never by the
launcher:

```
flags  >  L4 user override  >  L3 compat DB  >  L2 GOG-native  >  L1 auto renderer  >  L0 default runtime
```

The launcher only sources files gogo wrote, compares a stamp, and either execs Wine or
asks gogo to bring the prefix up to date first.

`--portable` (#84) keeps today's fat bundle (engine + prefix + game inside the `.app`) for
copying to another Mac. Everything below is about the default, non-portable bundle.

## 1. Decision 1: `gogo-launch.toml` is the source of truth, `launch.conf` is its mirror

**Settled:** the TOML is the source of truth. gogo also writes a shell-sourceable
`launch.conf` generated from it. The bash launcher only ever **sources `launch.conf`**,
and only gogo writes either file.

**Why:** bash can't parse TOML without a dependency the launcher shouldn't have (a
second binary inside the bundle, or `python3`, which macOS no longer ships). TOML stays
the format gogo reads, diffs and validates. The mirror is a mechanical projection, so
the two can't drift as long as gogo is the only writer.

### 1.1 Schema (`schema = 1`)

```toml
schema   = 1
gogid    = "1146738698"
title    = "Carmageddon TDR 2000"
runtime  = "winecx/24.0.7_7"          # <id>/<ver> in the store (decision 6)
renderer = "wined3d"                  # wined3d | dxmt/v0.80 | cnc-ddraw/7.1.0.0 | d3dmetal/<ver>
exe      = 'C:\GOG\Carmageddon TDR 2000\TDR2000.exe'
workdir  = 'C:\GOG\Carmageddon TDR 2000'
args     = ["-f"]
env      = { WINEMSYNC = "1" }
dll_overrides = { ddraw = "n,b" }     # what the launcher exports in WINEDLLOVERRIDES
verbs    = []                         # L1 winetricks verbs (#72); setup layers L3/L4, never the launcher

[gogo]
path  = "/Users/me/.nix-profile/bin/gogo"   # recorded at build (decision 2)
state = "/Users/me/Library/Application Support/gogo"
```

- Unknown keys are an error for gogo (`deny_unknown_fields`); `schema` gates any future
  change. A bundle with a newer `schema` than the running gogo is refused with "upgrade
  gogo", never half-read.
- `gogo.path` is the path gogo was **invoked as**, not `canonicalize`d: a Nix or Homebrew
  profile symlink survives upgrades, while the resolved `/nix/store/…` path does not.

### 1.2 Two copies of `launch.conf`

| File | Written by | When | Contents |
|---|---|---|---|
| `Foo.app/Contents/Resources/launch.conf` | gogo build | once, before signing | mirror of the bundle's TOML (L0–L3 + build flags as baked) |
| `games/<gogid>/launch.conf` | `gogo mac-app setup` | build, and whenever the stamp is stale | the **effective** config: bundle TOML with L4 applied, plus `RUNTIME_DIR`, `PREFIX`, `STAMP` resolved to absolute paths |

The launcher sources the bundle copy first, then the state copy if it exists. Values are
POSIX single-quoted by the same `sh_quote` the current `bundle.rs` uses. No
command substitution and no code, only assignments.

*Implemented in #66 (`macapp/launch.rs`), with these details:*

- Lists are bash arrays (`ARGS=('-f')`, `ENV=('K=V')`, `VERBS=()`);
  `DLL_OVERRIDES` is Wine's own `k=v;k2=v2` string.
- The state copy also carries `WINE`, `WINESERVER` and `FRAMEWORKS`, next to
  `RUNTIME_DIR`, `PREFIX` and `STAMP`.
- Paths under the state dir are written **relative to it**
  (`PREFIX='games/<gogid>/prefix'`), not absolute, and the launcher resolves them
  against the state dir it finds: `gogo.state` if that directory exists, else
  `~/Library/Application Support/gogo`. A state dir copied to another account (the VM
  harness, a new Mac) then works unchanged. Runtimes outside the store stay absolute.
- A runtime outside the store (brew, a GPTK mount, `--runtime path`) is referenced as
  `runtime = "path:<root>"`. It works, but it can't be swapped or GC-tracked.
- Build flags are baked into the bundle TOML (this table's first row). L4 is written
  by `--retarget` (§7), the early-exit dialog's "Try next renderer" (§8.2), the user,
  and a build whose `--renderer` / `--runtime` meets an L4 value for the same key
  (decision 5, #110). A build never creates an override file the user didn't ask
  for.

*#70 (renderers):*

- `renderer` is a ref `<id>[/<ver>]`: `wined3d`, `dxmt/v0.80`, `cnc-ddraw/7.1.0.0`,
  `d3dmetal/4.0b3` (#71). A ref without a version means the catalog's pinned one.
- `runtime` stays the **base** runtime. The derived runtime a DXMT game runs from
  (§3) appears only in the state `launch.conf` (`RUNTIME_DIR`, `RUNTIME`) and in
  `state.toml`'s `runtime`, so a later switch away from DXMT needs no rebuild.
  (#70's text had the TOML name the derived id; this keeps decision 3's "the
  launcher doesn't know about derivation".)
- The renderer's own overrides (`ddraw=n,b`) are **not** baked into
  `dll_overrides`: setup adds them for the effective renderer, and an explicit
  `dll_overrides` entry (baked or L4) for the same DLL wins. So the §1.1 example's
  `dll_overrides = { ddraw = "n,b" }` is what the state `launch.conf` ends up with,
  not the bundle TOML.

*#107 (entry point):* `exe` defaults to the `goggame-<id>.info` task chosen by
`macapp/info.rs`: the `isPrimary` `FileTask`, **unless its `category` is
`launcher`** — then a `category = "game"` task wins, hidden (`isHidden`) or not. A
primary launcher stays the pick only when no game task exists on disk; with no
primary at all, the first runnable task is used. GOG ships `GoGLauncher.exe` as the
primary task for some games (Rebel Galaxy, 1435582019) and it needs MFC runtimes a
fresh prefix lacks (`mfc110u.dll`, exit 53), while the game exe runs. `workdir`
follows the chosen exe's directory; `args` are not taken from `playTasks` yet.

## 2. Decision 2: gogo builds the prefix; the launcher re-runs setup only when stale

**Settled:** gogo creates and populates the prefix **at build time**, into
`games/<gogid>/prefix`. The launcher calls `gogo mac-app setup <gogid>` (the absolute
path recorded in `gogo.path`, then `gogo` on `PATH` as a fallback) **only** when the
config stamp is stale or the prefix is missing. If it can't find gogo, it launches as-is
and logs that.

**This departs from docs/19 §6.5**, which says the prefix is "created on first launch by
the user's own wine", with first launch running "create prefix → apply L2/L3/L4 → launch".
What changes, and why:

- **Same user, same Mac, so "the user's own wine" is still what runs.** Non-portable
  bundles are built by the person who plays them, into their own state dir, with the
  runtime from their own store. The prefix gets the right username without waiting for
  first launch. The builder-home leak (#55) came from Wine's default home-folder symlinks
  and `z:` → `/`, and decision 4 removes those. Who runs `wineboot` was never the cause.
- **The tools are present at build time and not in the launcher.** Prefix setup needs
  winetricks, gogo's `cabextract`/`7z` shims (design 12 D5), verb downloads (network),
  and registry writes. Putting that in a bash launcher would mean shipping or locating
  all of it at double-click time. gogo already has it.
- **Failures surface where they can be read.** A failed verb or `wineboot` at build
  prints in the terminal next to the command that caused it. At first launch the same
  failure would turn into a dialog after a long silent pause, and a broken prefix.
- **First launch is fast and boring.** The double-click does what the user expects.
- **docs/19's "first launch" behaviour is kept where it matters.** The stamp check means
  an edited L4 override, a `--retarget`, or a deleted prefix is applied on the next
  launch, without a rebuild, exactly as docs/19 wanted. Only the *first* setup moved
  earlier.

What it costs: a non-portable bundle copied to another account or Mac has no prefix
there. It needs gogo installed on that side to be set up (or the bundle should have been
built `--portable`).

### 2.1 The stamp

- `STAMP` = sha256 over the **inputs** of the effective config, in a fixed order: the
  bundle's `gogo-launch.toml` bytes, then the L4 file's bytes (or an empty marker when
  there is none; #66 uses zero bytes, so a missing and an empty L4 file stamp alike). The launcher can compute exactly this with `/usr/bin/shasum -a 256`
  and nothing else.
- `setup` records the stamp it applied in `games/<gogid>/launch.conf` (`STAMP=`) and in
  `state.toml`.
- Launcher: prefix missing, or computed stamp ≠ recorded stamp → run setup, then
  re-source the state `launch.conf`. Setup is idempotent: it re-applies registry, verbs,
  overrides and renderer files, and never deletes the prefix or the saves in it.
- L3 updates (a newer compat DB) reach a game when gogo next runs `setup` for it, not on
  every launch. The launcher doesn't know the DB exists.

### 2.2 `gogo mac-app setup <gogid>`

Reads the bundle TOML (path recorded in `state.toml`), L3 and L4, then installs or derives
the runtime it needs (decision 3, network allowed under design 12 D8), creates or updates
the prefix, writes the state `launch.conf`, and exits 0. Exit codes as for `mac-app`
(07 §2). The same function runs at the end of every build, so build and launch never
take different paths into the prefix.

*Implemented in #67 (`macapp/setup.rs`):*

- A store runtime that's missing is installed from the catalog (`<id>/<ver>` pins the
  version). A runtime it can't install (not in the catalog, or a consent download)
  fails with the `gogo runtimes install …` command to run.
- The prefix is created with `wineboot -u` and kept free of links out of the state
  dir (decision 4) on every run, not only at creation.
- Applied on every run: registry values from L3 then L4 (merged per decision 5;
  `gogo-launch.toml` has no `registry` field), then the effective `verbs` through
  winetricks and gogo's shims. winetricks skips verbs that are already installed.
  Verbs run their downloads by unix path, so `z:` is restored for the winetricks
  run and removed after it.
- *#70:* the effective renderer is applied on every run, before registry and
  verbs: DXMT → the derived runtime (installed from the renderer store, built
  if missing) becomes the runtime for the rest of setup and for the launcher;
  cnc-ddraw → `ddraw.dll` + gogo's `ddraw.ini` in the game dir and `ddraw=n,b`;
  wined3d → nothing. Moving off cnc-ddraw removes gogo's `ddraw.dll`/`ddraw.ini`
  again (only when the ini is gogo's). A renderer that can't be set up (no CX
  engine for DXMT, a `path:` runtime, a failed download, D3DMetal without consent)
  falls back to wined3d with a warning: a launch never fails on the renderer
  alone. `RENDERER` in the state `launch.conf` is what was actually applied.
  The runtime #72 compares for verb re-runs is the one actually run, so a switch
  onto or off DXMT re-runs winetricks once (it skips installed verbs), and the
  wrappers for a derived runtime are its own. One import scan feeds both L1
  fields (renderer and verbs) per build.

*Verbs, #72 (`macapp/verbs.rs`):*

- **L1 auto verbs.** The build scans the game's imports (#63 `helpers`: static
  imports minus DLLs the game ships, never runtime-loaded names) and maps each
  DirectX helper DLL to the winetricks verb that installs Microsoft's copy:
  - `d3dcompiler_42/43/46/47`, `d3dx9_24…43`, `d3dx10_43`, `d3dx11_42/43` and
    `d3dcsx_46/47` map to verbs of the same name;
  - any other `d3dx10_*` maps to `d3dx10`;
  - `xinput1_1…1_3` map to `xinput`;
  - XACT, X3DAudio, XAPOFX and `xaudio2_0…2_7` map to `xact` (`xact_x64` for
    64-bit importers).

  `xinput1_4`, `xinput9_1_0` and `xaudio2_8/2_9` ship with Windows, so they're
  Wine builtins and get no verb. The pre-confirm summary shows each verb with
  the imports behind it and its layer. The installer lane decides its verbs
  after the install.
- **Where each layer lives.** The bundle TOML's `verbs` holds **L1 only**; it is
  the build's list, so it is part of the stamp. Setup merges L3 (the compat DB,
  read live, like `registry`) and then L4 over it, each replacing the list
  whole. `gogo mac-app compat <gogid>` shows the winner with its layer, and it
  reads L1 from the built bundle.
- **Re-runs.** winetricks runs only when the effective list differs from the one
  `state.toml` recorded (`verbs`), when the runtime changed, or when the prefix
  is new. A stale stamp alone (an L4 `env` edit) doesn't re-run it.
- **SIP and winetricks.** winetricks is a `/bin/sh` script and calls wine through
  `/usr/bin/env`. SIP drops `DYLD_*` whenever a protected binary starts, so an
  inherited `DYLD_FALLBACK_LIBRARY_PATH` never reaches a CX24 wine. So `WINE` and
  `WINESERVER` point at small wrapper scripts (`runtimes/tools/shims/wine-<hash>/`)
  that export it themselves before `exec`. `WINE64` is set to the same wrapper,
  because winetricks otherwise derives `${WINE}64`, which a wow64 engine lacks.
- Setup returns only after `wineserver -w` (with `-k` after 60 s), so nothing writes
  into the prefix later.

## 3. Decision 3: renderers that replace Wine builtins live in a derived runtime

**Settled by #94** (overturns the pre-filled default "PE DLLs per prefix, `winemetal.so`
added to the store runtime").

Tested on `WineCX24.0.7_7` with `dxmt-v0.80-builtin.tar.gz`, using a windowless
`D3D11CreateDevice` probe, `WINEDEBUG=+loaddll` and `DYLD_PRINT_LIBRARIES` (the full
matrix is in the #94 comment):

| Placement | Result (64- and 32-bit) |
|---|---|
| `WINEDLLPATH=renderers/dxmt/v0.80` | wined3d loads; the engine's own `lib/wine` is searched first |
| PE DLLs in `system32`/`syswow64` + `n,b` | wined3d loads; the DLLs carry the builtin marker, so Wine swaps in the engine's copies |
| `winemetal.so` added to the store runtime + PE per prefix | wined3d loads; the `.so` is inert |
| **APFS clone of the engine + DXMT over `lib/wine/`** | **DXMT loads**: FL 11.0, `winemetal.so` `dlopen`ed from the derived tree |

Wine's loader (`dlls/ntdll/unix/loader.c`, the same in 9.0 and 11.0) always puts the
engine's own dll dir ahead of `WINEDLLPATH`, and it finds a unix lib only next to the
builtin PE it loaded. A shared, unmodified runtime therefore cannot be made to load
DXMT from outside its tree.

**Rule:**

- A renderer is either an **engine overlay** (it replaces Wine builtins: DXMT and
  D3DMetal) or **game-local** (cnc-ddraw: a DLL in the game dir +
  `dll_overrides`). wined3d is the engine itself and needs nothing.
- An engine-overlay renderer is installed as a **derived runtime**
  `runtimes/<id>/<ver>+<renderer>-<rver>/engine`. gogo builds it by `clonefile`ing the
  base engine and copying the renderer's `<arch>-windows`/`<arch>-unix` dirs over
  `lib/wine/`. `Frameworks/` is shared with the base: a relative symlink, since the
  engine reaches it through `DYLD_FALLBACK_LIBRARY_PATH`, not its `@rpath` (#62,
  decision 6). Measured cost: 0.75 s and ~1 MB of metadata for
  the 503 MB CX24 engine, plus the renderer's files once (~51 MB for DXMT), shared by every
  game that uses the same pair.
- The base runtime is **never modified**. A derived runtime is immutable once built:
  when either input is bumped, gogo builds a new one; it never patches one in place.
- The launcher doesn't know about derivation. The state `launch.conf` carries the
  resolved `RUNTIME_DIR`.
- No prefix copies and no `n,b` overrides for engine-overlay renderers.
- *#70:* the derived runtime is a normal entry in the runtime manifest
  (version `<ver>+dxmt-v0.80`, `upstream_url = derived:<base>+<renderer>`), so
  `resolve_ref` and `runtimes list` see it. Unpinned lookups (`installed(id,
  None)`) never pick a derived version. Its `NOTICES.txt` is the base's plus the
  renderer's. DXMT is overlaid only onto a CrossOver-source engine (the
  `winemac.drv` hook, docs/19 §3.2); another engine falls back to wined3d.
- *#71 (D3DMetal):* the same mechanism. The payload is the Sikarugir Template's
  kit (below). Its `wine/x86_64-{unix,windows}` go over `lib/wine/` like DXMT's
  arch dirs. Its `external/` (`D3DMetal.framework`, `libd3dshared.dylib`) becomes
  the engine's `lib/external/`, the layout Sikarugir uses. The kit's `d3d11.so`,
  `d3d12.so`, `dxgi.so` and the rest are symlinks to
  `../../external/libd3dshared.dylib`. That library loads `D3DMetal.framework`
  beside it through an `@loader_path` rpath, so the launcher needs no `DYLD_*`
  variables. The overlay keeps symlinks (those links, and the framework's
  `Versions/Current -> A`). The result is `winecx/24.0.7_7+d3dmetal-4.0b3`. The
  first host pass (2026-10-23) put `external/` next to the unix libs instead. The
  links dangled, and Unity reported "could not load d3d11.dll". A Wine loader test
  with `lib/external` resolves `D3D11CreateDevice` and goes on to load
  `dxgi.dll`.
- *#70:* fat (`--portable`) bundles can't carry a derived runtime: DXMT there
  falls back to wined3d with a warning. cnc-ddraw keeps design 13's build-time
  path (game dir + a registry `ddraw=n,b`).
- **arm64ec:** the overlay copies whatever `<arch>-*` dirs the renderer release ships
  (`aarch64-windows`/`aarch64-unix` for an ARM64EC DXMT), and the loader rule doesn't
  depend on arch. See §Open for entitlement-signed runtimes.

## 4. Decision 4: home folders are real dirs, `z:` is gone

**Settled:** `drive_c/users/<user>/{Desktop,Documents,Downloads,Music,Pictures,Videos}`
are plain directories inside `games/<gogid>/prefix`. They are never symlinks into the
real `~`. `dosdevices/z:` is removed.

*Implemented in #67, slightly wider than written:* a fresh prefix has more links out
than these (tested on CX24, 2026-10-23):

- `AppData/Roaming/Microsoft/Windows/Templates` → `~/Templates`;
- a drive letter for every volume the builder had mounted, e.g. `e:` →
  `/Users/<builder>/Library/Developer/…`, simulator runtimes, plus their raw `x::`
  devices.

So the rule is that every symlink under `drive_c/users/` with an absolute target
becomes an empty real dir, and `dosdevices/` keeps only `c:`. Wine maps the player's
own removable volumes again at run time. A later `wineboot -u` leaves the real dirs
alone.

The CX engine names the Windows user `crossover` whoever builds, so the builder's
username doesn't appear either. Build steps that run unix-path installers still
need `z:`: a new prefix drops it only after the build, and a reused one gets it back
for the build.

**Why:** saves and logs stay with the game (Rebel Galaxy wrote into the host's
`~/Documents/My Games/` during docs/19 §5), nothing escapes into the user's real folders,
and nothing in the prefix points outside the state dir. That last point is what made
#55's signature and username leaks possible. Dropping `z:` also means a game can't
wander the whole filesystem by accident.

**Consequence:** the game dir must be reachable without `z:`.
`prefix/drive_c/GOG/<tree-name>` is a relative symlink to `../../../game`, so the
Windows path stays `C:\GOG\<tree-name>` as in design 15, and registry keys and
`goggame-*.info` paths don't change.

## 5. Decision 5: precedence

**Settled:** `flags > L4 > L3 > L2 > L1 auto > L0 default`, field by field.
Maps (`env`, `dll_overrides`) merge per key; every other field, lists included, is
replaced whole, so an L4 `verbs = []` clears L3's verbs (#65, `macapp/compat.rs`).

**Why:** the closer a source is to the user's explicit intent, the more it wins. Curated
data (L3) beats heuristics (L1) because it records an observed result. GOG's own data (L2)
beats the import heuristic because it comes from the vendor.

- Flags only exist on a gogo invocation (`mac-app`, `setup`, `--retarget`). A flag that
  has to **persist** (`--renderer`, `--runtime`) is written into L4 (§7); a flag that
  doesn't is used for that run only. This keeps "flags > L4" true without a sixth
  persistent layer, and it's what decision 7 already does for `--retarget`.
- *#70, as implemented:* the build bakes `flags > L3 > L2 > L1 > L0` into the bundle,
  and setup applies L4 on top. `gogo mac-app compat <gogid>` traces the renderer back
  to its layer (a baked value that L0–L3 don't produce is reported as a build flag).
- *#110, as implemented:* baking alone would let an existing L4 value beat a build
  flag, and L4 is written by `--retarget` and "Try next renderer", so after one use a
  later build flag would silently lose. So when a build-time `--renderer` or
  `--runtime` is given **and** the L4 file already sets that key, the build also
  writes the flag's value there (`toml_edit`, just before the build's setup run) and
  reports it like `--retarget` does (`<gogid>: renderer dxmt/v0.80 -> wined3d
  (<path>)`; a `UserOverrideSet` event under `--json-progress`). A key L4 doesn't
  set, or no L4 file at all, gets nothing written: the flag is only baked. What counts
  as the flag: `--renderer <r>` when it actually won the merge (a `--renderer
  d3dmetal` that the #71 gate sets aside, 32-bit or no consent, writes nothing;
  `--no-ddraw-wrapper` never does), and `--runtime <src>` or a pick in the bare
  `--runtime` / `--interactive` menu (#76), written as the resolved ref
  (`wine-devel/11.19`, `path:<root>`). The `auto` ladder writes nothing, so an L4
  `runtime` keeps winning there.
- gogo edits only the keys it owns in the L4 file (`toml_edit`, so the user's comments
  survive) and reports what it changed.
- *#74 (compat entries at build and setup), as implemented:* `plan` merges L3 and L4
  for the game (`compat::db_and_user`) and shows `Effective::status_line` before the
  confirmation (`compat:    known to boot on winecx-24.0.7_7 (2026-10-22)`, `untested`,
  `known broken: <notes>`; `notes` is a new one-line schema key) and as
  `compat_status` in `--json`; `gogo mac-app compat` prints it too. Where each field
  goes:

  | Field | Build (baked into the bundle TOML) | Setup |
  |---|---|---|
  | `exe` | L3 replaces the `info.rs` / recipe entry point (warns and keeps it when the file isn't there); `workdir` follows | L4 over the baked one (`with_override`) |
  | `args` | L3 replaces the recipe's | L4 |
  | `env`, `dll_overrides` | L3 per key over the recipe's | L4 per key; renderer overrides only fill gaps |
  | `renderer` | L3 in `renderer::select` (#70) | L4 |
  | `runtime` | L3 pins the `auto` ladder (cached → used; headless and not cached → downloaded; interactive → the menu, with a warning); flags still win | L4 (installed if missing) |
  | `verbs` | not baked (the TOML keeps L1) | L3 then L4 replace L1 whole, via winetricks |
  | `registry` | not baked | L3 then L4, `reg add` through `interpret::run_in_prefix` |

  DLL overrides stay a launch-time `WINEDLLOVERRIDES` (§1.1), not registry writes, so
  an L4 edit takes them away again without touching the prefix. `replace_command` is
  parsed but not applied yet. `GOGO_COMPAT_DIR=<dir>` shadows the compiled-in DB with
  `<dir>/<gogid>.toml` files (still L3): for trying an entry before contributing it,
  and for the integration test (`compat_entry_drives_build_and_setup`).
- `gogo mac-app doctor` (#79) shows the winning layer for each field.

## 6. Decision 6: store layout and GC

**Settled:**

```
runtimes/<id>/<ver>/{engine,Frameworks}           base runtimes, as pinned (sha256) and probed
runtimes/<id>/<ver>+<renderer>-<rver>/engine      derived runtimes (§3)
renderers/<id>/<ver>/<arch>/                      renderer payloads, <arch> = runtime arch (x86_64, arm64ec)
games/<gogid>/{prefix,game,state.toml,launch.conf}
```

- *#70:* renderers have their own `renderers/manifest.json` (same record as the
  runtime manifest). `<arch>` holds the archive as downloaded (DXMT:
  `x86_64/v0.80/{x86_64-windows,i386-windows,x86_64-unix}`; cnc-ddraw: the zip's
  files) plus a `NOTICES.txt`. Only `x86_64` exists today. Both entries are pinned
  by sha256 (`dxmt-v0.80-builtin.tar.gz`; cnc-ddraw `v7.1.0.0`, whose release has
  no GitHub digest). cnc-ddraw moved here from `runtimes/cnc-ddraw/`: the old
  cached copy is ignored (re-downloaded once, 2.6 MB) and `gogo runtimes prune
  cnc-ddraw` removes both.
- *#70:* `prune` checks `state.toml`'s `renderer` as well as its `runtime`; `runtime`
  there is the runtime actually run, so a game on DXMT protects
  `<id>/<ver>+dxmt-<rver>` (and, through the shared id dir, its base).

- `state.toml` records the bundle path, the runtime and renderer refs in use, the applied
  stamp, and gogo's version. It's the store's **reference list**.
- **GC:** `gogo runtimes prune` never removes a runtime (base or derived) or a renderer
  that any `games/*/state.toml` references, and it always keeps the previous version
  (N-1) of each runtime id for rollback. There is **no automatic prune**.
- `games/<gogid>/` is removed only by an explicit command (it holds saves). A rebuild of
  the same game re-clones `game/` and keeps `prefix/`.
  *#66:* the installer lane learns the gogid only after installing, so it builds in
  `games/.build-<slug>-<pid>/` and then moves the result into place. If an older
  `prefix/` exists for that game, it's renamed to `prefix.old-<timestamp>`, never
  deleted. The depot lane keys the dir by `rootGameId` from `goggame-*.info`.
  `gogo runtimes prune` already refuses ids that a `state.toml` references. The N-1
  rule is left for the GC work.
- *#69, as implemented:* the reference list is `store::references()`: every
  `games/*/state.toml` (`runtime`, `renderer`) and every L4 file (`runtime`,
  `renderer`). The L4 file counts because it is what the next setup will run: a game
  retargeted to a runtime that isn't applied yet still protects it. The bundle's own
  `gogo-launch.toml` doesn't count: gogo can't enumerate bundles, and once nothing else
  names the baked runtime, setup installs it again from the catalog if L4 is dropped.
  `prune` takes `<id>` (every version) or `<id>/<ver>` (one version, with the derived
  runtimes built on it). A reference keeps a target when it names the same id and,
  for a versioned target, the same version or a derived runtime on it
  (`winecx/24.0.7_7+dxmt-v0.80` keeps `winecx/24.0.7_7`). A version-less reference
  (`runtime = "winecx"` in L4) keeps the newest base version, the one it resolves to.
  The check lives in `store::prune` itself, which reports what it kept and why. N-1
  belongs to the sweep, not to `prune <target>`: `gogo runtimes prune --all` offers
  every cached version except the newest two base versions of each id (by fetch
  time), so the previous pin survives a sweep, used or not, for rollback. Derived
  runtimes get no N-1: only a reference keeps them, since setup rebuilds one from its
  base in seconds. An explicit `prune <id>[/<ver>]` removes anything unreferenced:
  that is the user saying so. Installing a new pin still prunes nothing.
- Today's flat entries (`runtimes/wine-staging/11.18/…`, design 12 §4) stay readable:
  an entry without `engine/` is treated as an engine with no `Frameworks/`.
- *#62 (the CX engine, `winecx/24.0.7_7`):* the entry is
  `runtimes/winecx/24.0.7_7/{engine,Frameworks,NOTICES.txt}`. `engine/` is the
  contents of Sikarugir's `wswine.bundle`. `Frameworks/` holds the top-level `*.dylib`s
  (symlinks kept) of Sikarugir Template 1.0.24's `Contents/Frameworks`;
  `GStreamer.framework` is left out. `NOTICES.txt` holds the engine's licence and one
  licence line per dylib, and builds copy it into the bundle as `LICENSE-runtime.txt`.
  Both archives are pinned by sha256 in the catalog, and GitHub's asset digest must
  agree. Sikarugir publishes every engine under a single `v1.0` release, so the pin
  names the asset, not the tag. The install is probed with `wine --version` and
  `wineserver --version` (wineserver links `libinotify`).
- *#62, how the engine finds `Frameworks/`:* through `DYLD_FALLBACK_LIBRARY_PATH`,
  set by gogo on every Wine call (probe, `wineboot`, `reg`, installers, winetricks) and
  by the launcher from `FRAMEWORKS`. Mimicking the wrapper's
  `Contents/Frameworks/wswine.bundle` layout isn't enough: the rpath
  (`bin/../../`) would find the dylibs, but win32u `dlopen`s FreeType by leaf name,
  which only the fallback path finds. Without it, "Wine cannot find the FreeType
  font library" appears even in that layout (tested 2026-10-23). With the fallback
  path set, the layout doesn't matter, so decision 6's `{engine,Frameworks}` is
  kept as written. For §3's derived runtimes this means `Frameworks` is a relative
  symlink to the base entry's `Frameworks/`, and nothing is copied.

**Why:** one copy of each engine per Mac (bundles today carry 0.5–0.85 GiB of runtime
each, docs/19 §5), runtimes swappable in place (the macOS 28 path, docs/19 §7.3), and
game files and saves that survive a bundle rebuild.

## 7. Decision 7: `--retarget` writes L4, never the bundle

**Settled:** `gogo mac-app --retarget <bundle|gogid> --runtime <id>` (and `--renderer`)
writes the choice into `compat/<gogid>.toml` (L4). The signed bundle is never touched.
The next launch sees the stamp change and runs setup.

*#69, as implemented:* `--retarget` writes L4, then runs setup itself when the game
has a `state.toml` (and something changed), so a missing runtime is installed and a
failure shows up on the terminal instead of at the next launch. If that setup fails,
L4 stays written and the command exits non-zero; the next launch tries again. Setup
resolves the runtime as L4 `runtime` > `gogo-launch.toml` `runtime` (decision 5). When
the engine differs from the one `state.toml` last applied (comparing base runtimes,
so a renderer switch on the same engine doesn't count), setup runs `wineboot -u` on
the existing prefix before anything else, so the new engine updates the prefix before
the game starts rather than in the middle of it.

**Why:** the bundle seal stays valid (#53), retargeting is as cheap as editing a file,
and the user's override and gogo's retarget are the same mechanism, so `doctor` explains
both the same way.

## 8. Launcher contract (#66)

In order, in bash, with no other dependencies than `/usr/bin/shasum` and `osascript`:

1. `source Resources/launch.conf`, then `games/<gogid>/launch.conf` if present.
2. Compute the stamp (§2.1). If it's stale or the prefix is missing, run `gogo mac-app
   setup <gogid>` (`GOGO_PATH`, then `PATH`) and re-source. If there's no gogo, log the
   fact and continue.
3. Export `WINEPREFIX`, `WINEDLLOVERRIDES`, `env`; `cd` to the workdir; run Wine from
   `RUNTIME_DIR` with its log teed to `~/Library/Logs/gogo/<gogid>/` (#77).
4. If Wine ended early or failed, show the early-exit dialog (§8.2, #78). "Try next
   renderer" writes L4 through gogo, never directly.

*As implemented in #66:*

- Setup is called as `gogo mac-app setup <gogid> --bundle <this .app>`, so a bundle
  the user moved to `/Applications` updates `state.toml`.
- The launcher stays Wine's parent (it doesn't `exec`), so it can tear down.
- After Wine exits, the launcher waits on `wineserver -w`, because a launcher exe may
  have started the real game and exited.
- On `INT`/`TERM`/`HUP` it tears down (#42). It sends `TERM` to the game's process
  group, then runs the store runtime's `wineserver -k` with this prefix. If this
  prefix's wineserver is still alive after 5 s, it gets `SIGKILL`. That server is
  found by its cwd, `/tmp/.wine-<uid>/server-<dev>-<ino>` of the prefix: Wine's
  services `setsid()` into their own groups, so the process group can't be used to
  find them. What's left of the game's group also gets `SIGKILL`, and the launcher
  logs it.
- A `SIGKILL` of the launcher itself can't be trapped, so a watchdog does the
  teardown for it (#103), described next.
- *#103 watchdog.* Right after starting Wine, the launcher starts a background
  subshell in its own process group, with stdio on `/dev/null`, so it holds no end
  of the tee FIFOs and a terminal's Ctrl-C doesn't reach it. Every 2 s it checks
  that the launcher is still alive and is still the same process: not a zombie, and
  the same `ps -o lstart` start time, so a reused pid doesn't count. Once the
  launcher is gone (`SIGKILL`, Activity Monitor's Force Quit, a crash), it logs
  `watchdog: launcher <pid> is gone` to `launch.log` and runs the same teardown as
  the signal path. It then gives the tees 2 s to see EOF and `SIGKILL`s any that are
  left (they ignore `TERM`). It writes the run log footer `# exit: 137 (launcher
  killed)`, logs `watchdog done`, and exits. The launcher stops the watchdog (kills
  its process group) before every exit of its own: after `wineserver -w` on a normal
  end, and before the teardown in the signal handler. So the two never both tear
  down, and #78's relaunch, which `exec`s under the same pid, starts with no
  watchdog from the run before. Detection takes up to 2 s and the teardown up to
  about 5 s, so a `kill -9` leaves nothing after about 10 s.
- *Later launches of the same game.* Each running launcher writes
  `games/<gogid>/.launchers/<pid>` (its start time) and removes it on exit; the
  watchdog removes a dead launcher's file. If another launcher of this game is still
  running at teardown, the teardown leaves the shared wineserver alone (no
  `wineserver -k`, no `SIGKILL` of the server) and only ends its own game's process
  group. This applies to the signal path too. Stale files (a dead pid, or a reused
  pid with another start time) are ignored and removed.
- Logs go to `~/Library/Logs/gogo/<gogid>/`: `launch.log` and one run log per launch
  (§8.1, #77).

- *#69:* when setup fails, its last non-warning line goes into `launch.log` and into
  the run log header as `# setup: setup failed (exit <n>): <line>; running the last
  applied config`. The launcher then runs what the last setup applied. If that
  runtime's `wine` is gone from the store (pruned by hand, or a deleted tree), the
  launcher doesn't run anything. It writes a run log whose output says which runtime
  is missing and how to reinstall or retarget, with footer `# exit: 127 (runtime
  missing)`, shows a dialog, and exits 1.

The launcher never writes inside the bundle, never runs winetricks, and never modifies
the store.

### 8.1 Logs (#77)

`~/Library/Logs/gogo/<gogid>/` (`GOGO_LOG_DIR` overrides) holds two kinds of file:

- `launch.log`: the launcher's own journal, appended across runs. It records the
  launch, stamp checks, setup and its output, the `exec` line (which names the run
  log), Wine's exit, teardown reaps, and dialogs. It also covers launches that never
  reach Wine (no prefix, missing workdir).
- `<YYYYmmdd-HHMMSS>-<pid>.log`: one per Wine run, with `latest.log` a symlink to the
  newest. Only the newest 10 are kept: the launcher prunes by name (oldest first)
  each time it opens a new one.

A run log is a `# key: value` header, then Wine's stdout and stderr, then a footer:

```text
# gogo run log: Treasure Adventure Game (1207659013)
# started: 2026-10-23 14:25:01 +0200
# runtime: winecx/24.0.7_7
# runtime_dir: runtimes/winecx/24.0.7_7+dxmt-v0.80/…
# renderer: dxmt
# verbs: vcrun2019
# stamp: 3f0c…
# macos: 15.1 (24B83) arm64
# exe: C:\GOG\Treasure Adventure Game\Game.exe
# args: -windowed
# wine: /Users/me/Library/Application Support/gogo/runtimes/…/bin/wine
# prefix: /Users/me/Library/Application Support/gogo/games/1207659013/prefix
# ---
…Wine output…
# ---
# exit: 3
# duration: 2s
# ended: 2026-10-23 14:25:03 +0200
```

The header shows the effective config, i.e. the state `launch.conf` after setup, so it
includes L4. `runtime` is the reference and `runtime_dir` the engine Wine runs from (a
derived runtime for DXMT, §3). `exit` is Wine's exit code, or `<code> (SIG<name>)` when a signal
ended the run (`130`/`143`/`129`). `duration` runs from Wine's start until
`wineserver -w` returns. #78's early-exit dialog reads `exit` and `duration`. A
launcher killed with `SIGKILL` gets its footer from the watchdog (§8, #103): `# exit: 137
(launcher killed)`.

*Why per run and not one appended `wine.log`.* #66 teed Wine's output into an
unbounded `wine.log` and kept launcher events in `launch.log`. #77 replaces
`wine.log` with run logs rather than adding a second copy of the same output, and
keeps `launch.log` for what happens outside a Wine run. "The log for this run" is
then one self-describing file that a user can attach to a report, and that #78 and
`vm-test.sh` (`files.run_log`) can find without parsing timestamps.

*Tee mechanics.* Wine's stdout and stderr each pass through a FIFO into a `tee -a`
of the run log, so a terminal launch still shows both streams separately. The tees
ignore `INT`/`TERM`/`HUP`, so a Ctrl-C doesn't cut the tail of the log. Process
substitution won't do here: bash 3.2 can't `wait` for it, and the footer has to come
after everything Wine wrote. Before writing the footer, the launcher closes its ends
and waits up to 2 s for the tees to see EOF, then `SIGKILL`s them (they ignore
`TERM`); an orphan still holding Wine's output
open can't stall the exit. If `mkfifo` fails, output is appended to the run log
directly, without the tee.

### 8.2 Early-exit dialog (#78)

After the footer, a run that exited non-zero, or within `EARLY_EXIT_SECS` (15;
`GOGO_EARLY_EXIT_SECS` overrides), explains itself. A run ended by a trapped signal
doesn't: the user or a supervisor stopped it. The dialog is an `osascript display
dialog` titled with the game. It says how long the game ran, its exit code and the
renderer it ran on, and shows up to five lines of Wine output from the run log: the
last ones that look like errors (`err:`, `error`, `fail`, `exception`, `cannot`, `not
found`), or else the last five. Lines are cut to 160 characters. It has three
buttons:

- **Open log**: `open <run log>`, which shows it in Console.
- **Try next renderer**: `gogo mac-app next-renderer <gogid>` writes `renderer =
  "<next>"` to L4 (#65). The launcher then re-execs itself with the environment it
  started with, so the exports above don't stack up. The changed L4 file makes the
  stamp stale, so the relaunch runs setup, which applies the renderer: DXMT's derived
  runtime, cnc-ddraw in the game dir, or wined3d with both removed.
- **Copy report**: `pbcopy` of the game and gogid, the header's runtime, runtime_dir,
  renderer, verbs, stamp, macOS, exe and args lines, the exit and duration, and the
  last 40 lines of Wine output. The header's `wine:` and `prefix:` lines are left out,
  because they hold the user's home path.

The default button is the last one. The dialog gives up after 10 minutes, and giving
up does nothing.

*The next renderer.* This is `renderer::next_after(pick, current, d3dmetal)`:

- The order is the docs/19 §6.2 table's for this game, i.e. the L1 pick followed by its
  alternatives, from a fresh PE scan of the game's entry point.
- `current` is the renderer setup last applied (`state.toml`), not the configured one.
  A DXMT whose install failed already ran as wined3d, and retrying it would fail the
  same way.
- A `current` outside the order (L3, L4 or a build flag) starts the order from the
  top.
- D3DMetal is skipped unless `renderer::d3dmetal_available()`: a stored
  `[mac_app] d3dmetal = "yes"` (#71, below). The launcher's dialog runs headless,
  so it never asks. Without a yes, D3DMetal isn't in the order at all.

Before showing the dialog, the launcher asks `next-renderer --dry-run`. If that comes
back empty ("no more renderers", or no gogo, as in the VM guest), the dialog says
there is nothing left to try, and its third button is **Close** instead. The walk always
ends: each switch moves forward in a finite order, and every step is the user's click.

| L1 class | order |
|---|---|
| DirectDraw 2D, 32-bit | cnc-ddraw → wined3d |
| Direct3D 10/11 | DXMT → (D3DMetal, 64-bit with consent) → wined3d |
| Direct3D 12, 64-bit, with consent | D3DMetal → DXMT → wined3d |
| everything else | wined3d |

*D3DMetal consent (#71, docs/19 §3.2).* D3DMetal is Apple software under the Game
Porting Toolkit licence (EA18380). The licence allows distribution only for
non-commercial purposes, with Apple's notices kept (§2A(iii), §2C). gogo fetches it
only after the user agreed, and asks once:

- **Source.** Catalog entry `d3dmetal` (status `ConsentRequired`): the
  `renderer/d3dmetal` directory of the Sikarugir `Template-1.0.24.tar.xz`, pinned by
  sha256. It is the same asset and digest as winecx's `Frameworks/` set (96 MB
  download, 24 MB kept). Only that directory is extracted. It holds D3DMetal 4.0b3,
  its Wine-side `d3d11`/`d3d12`/`d3d12core`/`dxgi`/`nvapi64`/`nvngx`, and Apple's
  `License.rtf`, `Acknowledgements.rtf` and `Read Me.rtf`. This kit is the one that
  ran Neo Cab on the default CX24 engine (docs/19 §5). Gcenx's GPTK 3.0-3 pairs
  D3DMetal 3.0 with Wine 7.7 builtins, and gogo keeps it as a separate runtime
  (`gptk`).
- **The answer** lives in gogo's config: `[mac_app] d3dmetal = "yes"|"no"` (design
  05 §3). It is written with `toml_edit`, so the rest of the file is kept.
- **When it is asked**: at build time (`mac-app` plan, depot lane), for a **64-bit**
  game whose scan says Direct3D 12, for `--renderer d3dmetal`, or when the game's L3
  compat entry (#74) sets `renderer = "d3dmetal"`. `--retarget --renderer d3dmetal`
  asks too. An L3 D3DMetal without a yes, or on a 32-bit game, is set aside with a
  warning, so the layers below pick (DXMT for 64-bit D3D11), not setup's wined3d
  fallback. It is a Confirm prompt, default no, that names
  Apple's licence and the download size. The answer is stored either way.
  Cancelling stores nothing. A stored answer is never asked again. The installer
  lane scans only after installing, so it asks only for `--renderer d3dmetal` (at
  plan time), and a D3D12 game there uses the stored answer.
- **Headless with no answer** (no TTY, `--json`, the launcher's setup): no
  download. A warning names the config key, and the pick falls back (D3D12 →
  wined3d with the "likely broken" warning).
- **Never for 32-bit games**: no prompt, no D3DMetal in the L1 order, and
  `--renderer d3dmetal` on a 32-bit game warns and keeps the automatic choice.
  (A hand-written L4 `renderer = "d3dmetal"` is the user's own choice and is
  applied as written.)
- **Where it is used.** With a yes: the L1 pick for 64-bit D3D12, and the
  alternative after DXMT for 64-bit D3D11 ("Try next renderer"). DXMT stays the
  default there. `apply` without a yes falls back to wined3d before any download.
  `gogo runtimes install d3dmetal` works only with a yes.
- **Notices.** The store's `NOTICES.txt` carries the licence line and Apple's notice,
  and so does the derived runtime's (`LICENSE-runtime.txt` in bundles). A bundle
  whose baked renderer *or* "Try next renderer" alternative is D3DMetal gets
  `LICENSE-d3dmetal.txt` with the same notice.

Tests replace the dialog with `GOGO_LAUNCHER_DIALOG=<cmd>`. The command gets the
title, the message and the button labels, and prints the label it chose.
`GOGO_LAUNCHER_NO_DIALOG` without it only logs the early exit.

## 9. Testing (08 conventions)

- Unit: TOML ⇄ `launch.conf` projection (golden), stamp computation matching a
  reference `shasum` output, precedence merge per field, `prune` reference rules,
  derived-runtime overlay against a fake engine tree.
- Integration (`macapp_pipeline.rs`): build with a fake runtime → assert nothing under

  so while B runs. B removed: the launcher refuses with `# exit: 127 (runtime

- Unit (#71): D3DMetal consent with fake TTY prompts (yes and no are stored and never

  Template-subdir install (refused without consent, only the kit extracted, Apple's
  files and notice kept) and the derived runtime (host libs next to the unix libs,

- VM (#68): `scripts/vm-test.sh` gains a store and state-dir seeding step, since a v2
