# Design review — 2026-10-09

Critique pass over docs 01–09 + README, using the discovery research (docs/01–12) as ground
truth: load-bearing claims were re-checked against `docs/11` (live verification) and the
other discovery docs, and every finding below cites its evidence. Severity groups:

- **A — incorrect assumptions**: provable wrongness from our own discovery data or from the
  docs' own stated invariants. Contract bugs.
- **B — contradictions / unspecified behavior**: two docs disagree, or behavior a real
  implementation must choose is left open.
- **C — design smells**: works as written, but will bite.
- **D — minor polish.**

**Code status at review time:** the workspace scaffold exists (`7cff0b4`, split in
`9a3425a`) but modules are type-level stubs (~1.1k lines total; no engine behavior yet).
Findings are to be fixed **in lockstep**: doc edit first, then the module named in the
"Fixes" line — cheap now, expensive once the engine has real behavior.

## What checked out (no action)

For the record, the load-bearing live facts were re-verified against discovery and hold:
downlink shape `{downlink, checksum}` (docs/11 §3), checksum XML authoritative with 10 MiB
chunks (docs/11 §5), 403→skip for bundled extras, `expires_in = 3600` / no refresh rotation
(docs/11 §1), Bearer on embed endpoints, batch `?ids=`×50, public XML URL, unauthenticated

`TokenProvider`, per-chunk verification over whole-file re-read.

## A. Incorrect assumptions

### A1. Owned ids are not games

**Claim.** 03 §1: `list` sources = "owned ids (always live, 1 call) + catalog cache";
`download --all` = "every owned game". 01's `library.rs` row also mentions
"getFilteredProducts paging" with no stated role — 01 and 03 already disagree.

**Problem.** Our own live data: `/user/data/games` → **146 ids**, `getFilteredProducts`
(mediaType=1) → **83 products** (docs/11, "Live verification results"), and docs/10 §2 says
explicitly that owned ids "include bundles + DLC ids". Nothing in the design classifies
non-game ids: `list` renders DLC/bundle rows as top-level games, and `download --all`
downloads DLCs twice (own product entry + parent's `expanded_dlcs`).

**Fix.** Specify the classification step: either make `getFilteredProducts` the canonical
game list (paged, has `availability.isAvailableInAccount`, separates movies via `mediaType`)
and use owned ids only as a freshness cross-check, or compute the DLC-id set from catalog
`expanded_dlcs` and subtract it. State it in 03 §1 and the `library.rs` module row.

**Fixes:** docs 03 §1, 01 (`library.rs`) · code `gog/library.rs`, `engine/select.rs`.

### A2. The checksum XML can say "not available" — the parse model drops it

**Claim.** `ChecksumDoc { name, total_size, chunks[] }` (01 module tree, 04 §3).

**Problem.** Live-verified root attributes are
`<file name available notavailablemsg md5 chunks timestamp total_size>` (docs/11 §5). The
design discards `available`/`notavailablemsg`. An unavailable file lands in the "no-chunks
case → size-only verify, warn" path (04 §7), which is actively wrong — correct behavior is
skip-with-message using `notavailablemsg`.

**Fix.** Model `available` (and `notavailablemsg`) in `ChecksumDoc`; treat
`available=false` as a distinct resolution outcome: `Warn` + skip, never a download.
**Fixes:** docs 01, 04 §3 + §7 edge-case table · code `gog/checksum.rs`, resolve path in
`engine/mod.rs`.

### A3. "Bytes are sacred" holds for process crashes, not power loss

**Claim.** 07 §6: final-name files are always complete+verified (§6.1) and "any interruption
loses at most one chunk of progress" (§6.2).

**Problem.** The sidecar is tmp→fsync→rename (04 §5) but the `.part` **data** is never
fsynced — not per chunk, and not before the final `rename()` (04 §6). After a power/FS-level
crash the durable sidecar can claim chunk N done while N's bytes never reached disk. Resume
trusts `done` bits (08 §3 test 2 even asserts done chunks are never re-fetched), so the file
can finalize **corrupt** — silently violating the flagship invariant. Two distinct holes:
(a) resume trusts non-durable done-bits, (b) the final rename blesses non-durable data.

**Fix.** Minimum: fsync `.part` before the final rename (closes (b); one fsync per file).
For (a) pick one and write the trade-off into 04 §5: per-chunk fsync before the sidecar
rename (~100 fsyncs/GiB, simplest, still cheap vs network), or re-verify done chunks on
resume (local read + md5, no extra fsyncs), or explicitly scope the invariant to process
crashes and document power loss as out of scope. Whatever is chosen, 07 §6's wording must
state its actual durability scope.

**Fixes:** docs 04 §4–§6, 07 §6 · code `engine/worker.rs`, `engine/sidecar.rs`, finalize in
`engine/mod.rs`.

### A4. The rate limiter fails at its own documented floor

**Claim.** 04 §4: burst = `min(1 MiB, limit)`, per-read asks `until_n_ready(buf.len())` with
"32–64 KiB" reads; 05 §3 floor: limits below 32 KiB/s rejected.

**Problem.** governor's direct limiter returns `Err(InsufficientCapacity)` when a single ask
exceeds burst capacity. At `--limit 32kib/s` (the allowed minimum) burst = 32 KiB, so a
64 KiB read is *guaranteed* to error — and `resp.chunk()` sizes are not bounded by us
anyway. This fires only in integration, not in review.

**Fix.** Either set burst ≥ max possible single ask (e.g. `max(limit, 1 MiB)` — burst is
capacity, not rate), or clamp/split each buffer into capacity-sized asks. Add an integration
test at the floor limit (extend 08 §3 #10).

**Fixes:** docs 04 §4 (and 05 §3 note) · code `engine/limiter.rs`.

### A5. `verify-cache` key collides for DLCs

**Claim.** 06 §3: `verify-cache/{product_id}-{file_id}.xml`.

**Problem.** Records are keyed by the 3-tuple `(product_id, dlc_id, file_id)` precisely
because ids repeat across products — a DLC ships `en1installer0` just like its base game.
The 2-part cache key makes `gogo verify` check the DLC file against the base game's
checksum doc (or vice versa): false corrupt / false ok.

**Fix.** Include `dlc_id` in the filename (`{product_id}-{dlc_id|base}-{file_id}.xml`).
**Fixes:** docs 06 §3 · code `state/cache.rs` (or wherever verify-cache paths resolve;
`state/records.rs` consumers).

### A6. Keyring fallback: "logout" doesn't log out

**Claim.** 02 §3: keyring unavailable → "fall back to the file store for this run; the
config stays keyring"; `logout` clears the *active* backend.

**Problem.** Concrete failure chain: login during a secret-service outage → tokens land in
the file store; later `logout` on a healthy keyring clears the (empty) keyring only → file
tokens survive → `whoami` still authenticated after "logout". Mirror problem on load: once
the keyring is available again, an empty keyring shadows valid file tokens → user appears
logged out. The per-run fallback has no state machine.

**Fix.** Track which backend actually served/persisted the session (persist a small pointer,
or probe both on load preferring the fresher). `logout` clears the backend that holds the
session; consider making `--all-stores` the default for `logout`. Specify load fallback
symmetry (keyring-empty ⇒ try file) in 02 §3.

**Fixes:** docs 02 §3 · code `auth/store.rs`, `auth/mod.rs`.

## B. Contradictions / unspecified behavior

### B1. Non-TTY `download --all` without `--yes` is undefined

03 §3: "Never prompt when stdin/stdout is not a TTY" — and two lines later: "`--all` without
`--yes` shows the plan … and asks for confirmation". Headless behavior is unstated, and the
dangerous reading (proceed silently into a multi-hundred-GB run) is the easy one to
implement. Specify: non-TTY + no `--yes` → abort with the plan printed, exit 2 (consistent
with "ambiguous selection, non-TTY: exit 2").
**Fixes:** docs 03 §3 · code `gogo-cli/cli.rs`, `main.rs`.

### B2. `bearer()` once per command vs per-file resolution on multi-hour runs

02 §4 caches the token for the whole command; 04 §3 resolves downlinks "per file, every
run"; `expires_in = 3600`. Any `--all` run over ~1 h uses stale tokens and silently leans on
the 401→refresh→retry path as the *real* refresh mechanism. gog-warp caches and
lazy-refreshes inside `obtain_galaxy_token()`, so per-request `bearer()` costs nothing and
makes the 401 path what it should be: a safety net. Change 02 §4 to per-request.
**Fixes:** docs 02 §4 · code `auth/mod.rs` + the `gog/*` clients' auth header injection.

### B3. "Re-resolve once" on CDN 403 is arbitrary

CDN URLs embed `nva={expires_at}` (docs/04 §1.3) — they expire on a clock. A rate-limited
60 GiB file can outlive several token lifetimes; "re-resolve once" (04 §7, 07 §3) fails
polite long downloads by design. Make re-resolution an on-demand policy with a bounded
budget (like chunk retries), reset on success. Optionally parse `nva` from the URL to
proactively re-resolve before the 403.
**Fixes:** docs 04 §7, 07 §3 · code `engine/mod.rs` (resolve-on-403 loop), `engine/worker.rs`.

### B4. Plan-stage adoption contradicts "resolve at download time" and explodes for `--all`

04 §2 skip rule 4: dest exists, no record → "verify against checksum doc now (cheap,
local)". It is neither cheap nor local: it needs the checksum XML from the API (04 §3 says
resolution happens at download time) plus a full read of a possibly-60 GiB file — per
candidate, at plan time, before the confirmation prompt. On a pre-populated dir with `--all`
that's hundreds of API calls and hours of silent disk I/O. Move adoption into the execute
stage (resolve → verify → record → skip-download), or gate plan-time adoption behind a flag,
and say what the plan prints meanwhile (`pending adoption`).
**Fixes:** docs 04 §2/§3 · code `engine/select.rs` (plan), `engine/mod.rs` (execute).

### B5. `state.lock` scope: blocks readers, or protects nothing

06 §1: "an advisory fs4 lock … guards state.json against two concurrent gogo processes
(second process exits 1)". Records are appended at each `FileDone` (04 §6 step 4). If the
lock is held for the whole run, `gogo list` fails during any multi-hour download; if held
only per write, two downloads can write the same `.part`. Specify both levels: short
exclusive lock around each state.json read-modify-write (readers take it too, briefly), plus
a per-destination lock (flock on `{dest}.part` or `state.lock`-style sidecar) for download
exclusivity — second *download* of the same destination exits, second *reader* never does.
**Fixes:** docs 06 §1 (and 07 §6 invariant 4 wording) · code `state/mod.rs`, acquire in
`engine/mod.rs`.

### B6. The 30-min per-file budget may outlaw legitimate downloads

07 §3: "a file retried for more than 30 min straight → FileFailed". If "retried" is read as
total per-file time, a 60 GiB file at 2 MiB/s (~8.5 h) — or any rate-limited large file —
can never finish. State it precisely: the budget counts time spent in retry backoff / no
progress, never steady transfer; and it is per attempt-burst, reset on progress.
**Fixes:** docs 07 §3 · code retry budget in `engine/mod.rs`.

## C. Design smells

### C1. Exit-code "highest class" masks root causes; `DownloadError` has no Io variant

03 §5 / 07 §2 use numeric order 2<3<4<5<6 as severity. One expired-token 401 (3) + one
checksum mismatch (5) → exit 5, hiding the auth failure that explains the batch. Either
document the precedence rationale or use first-cause. Also: `DownloadError` (07 §1) lacks an
Io variant — an `ENOSPC`/`EIO` from `write_all_at` mid-chunk maps to "anything else → 1"
instead of 6; add `Io(#[from] std::io::Error)` with ENOSPC→DiskSpace mapping.
**Fixes:** docs 03 §5, 07 §1/§2 · code `gog/error.rs`, `gogo-cli/main.rs`.

### C2. Env naming rule contradicts its own table

05 §4 states `GOGO_<SECTION>_<KEY>`, then lists `GOGO_WORKERS`, `GOGO_LIMIT`,
`GOGO_TOKEN_STORE`, `GOGO_RETRIES` (section dropped) next to `GOGO_DOWNLOAD_DIR` (section
kept). Pick one scheme (flattened names are friendlier — then say the rule is "flattened,
table is normative").
**Fixes:** docs 05 §4 · code `config.rs` env overlay.

### C3. Client credentials have no override

docs/09 §1 names "keep credentials overridable via config" as *the* mitigation for the
shared-Galaxy-credentials risk; 02 §1 hardcodes them. If GOG rotates those public creds,
every gogo binary is dead until an upgrade. Add optional `[auth] client_id` / `client_secret`
(overriding gog-warp's constants if it allows injection; vendor-note otherwise). They are
public values — 05 §6's "no secret-bearing keys" is not violated.
**Fixes:** docs 02 §1, 05 §3 schema · code `config.rs`, `auth/mod.rs`.

### C4. Extras without checksum XML have no defined filename

04 §2: filename "from their checksum doc when available" — and when not? The API entry
`name` is a human label ("2 wallpapers"), not a filename; nothing in discovery or design
mentions `Content-Disposition`. 04 §7 covers verification for this case but not naming.
Specify the chain (checksum XML name → Content-Disposition → sanitized entry name + id) or
v1 will invent something divergent in implementation.
**Fixes:** docs 04 §2 + §7 · code `engine/task.rs`, `gog/downlink.rs`.

### C5. CDN 404 is missing from the retry matrix

07 §3 covers 416/403/5xx/md5-mismatch/truncation for chunks; a plain 404 (revoked link,
file replaced mid-run) is undefined, and `ApiError::NotFound(u64)` is shaped for product
ids. Define: CDN 404 → re-resolve once, then FileFailed (no retry loop).
**Fixes:** docs 07 §3 · code `gog/error.rs`, `engine/worker.rs`.

### C6. Sidecar rewrite is O(n²) in bytes

04 §5 rewrites the full sidecar per completed chunk. A 60 GiB file ≈ 6k chunks × ~600 KB
JSON ≈ **3.6 GB of sidecar writes per file**. Write the chunk table once at plan time;
persist progress as a compact done-bitmap (or append-only chunk-done log).
**Fixes:** docs 04 §5 (schema tweak) · code `engine/sidecar.rs`.

### C7. Build id parsed from the filename is a brittle single source

06 §3/§4: `build` comes from parsing `…_(<build>).exe` — a GOG naming convention, in a
codebase that insists on loose parsing because the API is contractless. The checksum XML's
`timestamp` is the same change evidence without the parse risk. Prefer timestamp for
`--strict` change detection, keep build as best-effort metadata, and make parse failure
non-fatal.
**Fixes:** docs 06 §3/§4 · code `state/records.rs`.

### C8. "Collision-proof by keeping the product id in the state record" is a non sequitur

04 §2: that makes *records* collision-proof; two same-titled products still share a
directory. Harmless (filenames differ) but the sentence misleads — reword to say paths may
collide benignly and records disambiguate.
**Fixes:** docs 04 §2 · code — (wording only).

## Recommended order

1. **A1–A6** — contract-level wrongness; fix docs and scaffold together before engine
   behavior exists (A3 and A4 are the two that get 10× more expensive after the engine
   works).
2. **B1, B3, B5** — underspecified in ways that produce bad implementations regardless of
   care.
3. **C3** — the discovery risk register asked for it; trivial while auth is a stub.
4. Remaining B, C, D ride along as doc edits + module notes during implementation.
